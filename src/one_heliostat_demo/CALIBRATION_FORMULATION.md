# Kinematic Calibration: the Aim-Point Formulation Problem

**Scope:** `src/one_heliostat_demo` two-stage training (`single_heliostat/train.py`).
**TL;DR:** Both Stage 1 (AlignmentLoss) and Stage 2 (FocalSpotLoss) currently inject a
*fictional aim point* (the receiver centre) that we don't actually have in real data. The
correct formulation uses only the two real observables — the **recorded motor positions**
and the **observed focal-spot centroid** — which happen to be the inverse and forward halves
of the *same* physical constraint. On synthetic data the current code looks fine because the
ground truth was generated by aiming at the centre; on real PAINT data the same code is
mis-specified.

---

## 1. The physical setup and what we actually measure

A heliostat reflects sunlight onto a tower receiver. Its pointing is governed by a
**kinematic model** with parameters `θ` (joint tilts, translation deviations, actuator
angles/offsets, base position). The model defines two maps, for a fixed sun direction `s`:

```
align    :  aim point  a   ──►   motor position  m       (inverse kinematics)
raytrace :  motor position m ──►  focal-spot centroid c   (forward optics)
```

`align` answers *"what motor counts put the beam on point `a`?"*. `raytrace` answers
*"given these motor counts, where does the beam actually land?"*. For a fixed sun, each is a
bijection between 2-DOF aim points and 2 motor positions (the supervisor's "bijective mapping"
remark).

**What a calibration sample physically contains:**

| Symbol | Meaning | Available in real data? |
|--------|---------|--------------------------|
| `s`      | sun / incident ray direction        | ✅ yes |
| `m_c`    | recorded motor positions            | ✅ yes (encoder readout) |
| `c_gt`   | observed focal-spot centroid        | ✅ yes (extracted from the flux image) |
| flux img | the focal-spot bitmap               | ✅ yes |
| aim point| where the operator *intended* to aim| ❌ **no** — never recorded |

The single ground-truth fact that physics gives us is:

```
        raytrace_true(s, m_c)  =  c_gt
        "these motors produced this spot"
```

Everything in calibration must be derivable from `(s, m_c, c_gt)`. **The intended aim point is
not an observable** — if a formulation needs it, that formulation cannot run on real data.

---

## 2. How the synthetic dataset is generated

`single_heliostat/generate_dataset.py` → `utils/synth_data.py::_forward_pass`:

1. Perturb the kinematics to a known ground truth `θ_GT` (this is the thing we want to recover).
2. Command the perturbed model to **aim at the receiver centre**:
   ```
   m_c = align(θ_GT, s, centre)
   ```
3. Ray-trace those motors to get the spot:
   ```
   c_gt = raytrace(θ_GT, s, m_c)
   ```
4. Save `m_c`, `c_gt`, the flux image, and `s` per sample.

Two facts to carry forward:

* **The spot is off-centre.** Even though we aimed at the centre, `c_gt ≠ centre`. This is
  *not* noise — it is the gap between `align` and `raytrace⁻¹`. `align` orients the rigid-body
  *reference* normal at the aim point, while `raytrace` reflects off the *real cantilevered /
  deflectometry surface*. Call that systematic optical offset `δ(θ, s)`:
  ```
  c_gt = raytrace(θ_GT, s, align(θ_GT, s, centre)) = centre + δ(θ_GT, s)
  ```
  The existence of `δ` is exactly why `align` and `raytrace` are **not** exact inverses.

* **`m_c` is defined as the aim-at-centre motors.** This is a synthetic artefact. On real
  hardware `m_c` comes from the plant controller (a *different*, nominal model, aiming at an
  *unknown* point). This single artefact is what makes the buggy formulations *look* correct
  on synthetic data.

## 3. Stage 1 — AlignmentLoss (the inverse map)

Stage 1 is a cheap, ray-trace-free supervision in motor space.

### 3.1 What the code does now

`train.py`, Stage 1 loop:

```python
hg.align_surfaces_with_incident_ray_directions(aim_points = centre, ...)
loss = AlignmentLoss(kinematic.active_motor_positions, train_motor_pos)   # = ‖m_pred − m_c‖
```

i.e. it minimises

```
L1_current(θ) = ‖ align(θ, s, centre) − m_c ‖
```

**The implicit claim:** *"`m_c` is the motor position for aiming at the centre."*

This is false. `m_c` is the motor position that produced `c_gt` — it points at `c_gt`, not at
the centre. We are attaching the motor label to the wrong aim point, off by exactly `δ`.

Why it nonetheless *works on synthetic data*: because `m_c := align(θ_GT, s, centre)` by
construction, `θ_GT` zeroes `L1_current` exactly. The loss is testing the model against its own
definition — circular. On real data, where `m_c` is not an aim-at-centre quantity, the circle
breaks and `θ_GT` is no longer the minimiser.

### 3.2 The correct formulation

Feed the model the aim point that `m_c` *actually* corresponds to — the observed centroid
`c_gt` — and match the motor position:

```
L1_correct(θ) = ‖ align(θ, s, c_gt) − m_c ‖
```

**The claim now:** *"to land the beam on `c_gt`, the model must use motors `m_c`."* That is the
true inverse-kinematic statement, and it is computable from real observables (`c_gt` is read
off the flux image).

### 3.3 Why it is better — three independent reasons

1. **Correct labelling.** It matches how real calibration works; the current version encodes a
   falsehood that only happens to be self-consistent on synthetic data.
2. **Breaks parameter degeneracy.** Aiming always at the centre probes the kinematic model at a
   *single* aim point, leaving a null space of parameter combinations that all yield the same
   centre-aiming motors. The observed centroids `c_gt` are scattered (the perturbation spreads
   them), so aiming at them exercises the model over a spread of aim points and shrinks that
   null space. (The dominant diversity still comes from the many sun directions `s`; the
   aim-point spread is a secondary but free gain.)
3. **Consistency with Stage 2.** Both stages then encode the same `m_c ↔ c_gt` constraint, so
   Stage 1 becomes a faithful initialiser for Stage 2 instead of pulling toward a different
   target.

### 3.4 The exactness caveat

`L1_correct` is a **proxy** for the true objective, because `align` is not the exact inverse of
`raytrace` (the `δ` offset). At `θ = θ_GT`:

```
align(θ_GT, s, c_gt) = align(θ_GT, s, centre + δ) ≈ m_c + J·δ   ≠ m_c
```

so the corrected Stage-1 loss does **not** reach exactly zero at the ground truth — there is a
residual of order `δ`. That is acceptable: Stage 1 is the cheap initialiser, and Stage 2
(the exact forward objective) removes the residual. The point of Stage 1 is speed (no ray
tracing), and `L1_correct` is a far better-conditioned proxy than `L1_current`.

### 3.5 Code change (small)

* Data generation: **no change** (keep aiming at the centre — it keeps spots on-target).
* JSON / parser: **no change** (`c_gt` is already saved as `focal_spot_enu`, already loaded as
  `train_centroids`).
* `train.py` Stage 1 loop and its validation sub-loop:
  ```python
  # before
  aim_points = scenario.solar_tower.get_centers_of_target_areas(train_target_mask, device)
  # after
  aim_points = train_centroids        # already [N, 4] ENU
  ```
* Evaluation: **no change** (eval should still aim at the centre and measure where the beam
  lands vs `c_gt` — that is the real focal-spot metric).

## 4. Stage 2 — FocalSpotLoss (the forward map)

Stage 2 is the expensive, ray-traced supervision in image/centroid space. It has the **same**
defect, mirrored.

### 4.1 What the code does now

`train.py`, Stage 2 loop:

```python
hg.align_surfaces_with_incident_ray_directions(aim_points = centre, ...)   # θ recomputes motors
flux = ray_tracer.trace_rays(...)                                          # θ traces optics
loss = FocalSpotLoss(flux, ground_truth = c_gt)
```

i.e. the predicted spot is

```
ĉ_current(θ) = raytrace(θ, s, align(θ, s, centre))
L2_current(θ) = ‖ ĉ_current(θ) − c_gt ‖
```

It **re-derives** the motors by aiming at the centre and never uses the recorded `m_c`. Same
fictional-aim-point assumption as Stage 1.

### 4.2 The correct formulation

Hold the **recorded motors** fixed and ask whether the model's optics land them on `c_gt`:

```
ĉ_correct(θ) = raytrace(θ, s, m_c)
L2_correct(θ) = ‖ ĉ_correct(θ) − c_gt ‖
```

This is the model's version of the one true physical fact `raytrace_true(s, m_c) = c_gt`.

### 4.3 The clean inverse/forward symmetry

| Stage | input you feed | model predicts | match against |
|-------|----------------|----------------|----------------|
| **1 — inverse** | observed spot `c_gt` | motors `align(θ, s, c_gt)` | recorded `m_c` |
| **2 — forward** | recorded motors `m_c` | spot `raytrace(θ, s, m_c)` | observed `c_gt` |

Both use only `(s, m_c, c_gt)`. Neither invents an aim point. They are the two halves of the
single constraint `m_c ↔ c_gt`. The current code breaks the symmetry by inserting an
`align(aim = centre)` step into *both* stages.

### 4.4 Why synthetic data hides it, real data won't

With `m_c := align(θ_GT, s, centre)`, at `θ = θ_GT`:

```
ĉ_current(θ_GT) = raytrace(θ_GT, align(θ_GT, centre)) = raytrace(θ_GT, m_c) = c_gt   ✓
ĉ_correct(θ_GT) = raytrace(θ_GT, m_c)                                       = c_gt   ✓
```

Both zero out — so on synthetic data `L2_current` is unfaithful but not broken. On **real**
data `m_c` is whatever the plant controller commanded (different model, unknown aim), so
`align(θ_GT, s, centre) ≠ m_c`, and therefore `ĉ_current(θ_GT) ≠ c_gt`: the ground truth no
longer minimises `L2_current`. `L2_correct` still holds because `raytrace(θ_GT, m_c) = c_gt`
is true by physics regardless of how the motors were commanded.

### 4.5 A practical bonus: better-conditioned gradients

In `L2_current`, `θ` enters **twice** — in `align` and again in `raytrace`. Because the two are
near-inverses, a parameter error partially cancels between them:

```
ĉ_current(θ) = raytrace(θ, align(θ, centre)) ≈ centre + δ(θ, s)
```

so you are effectively fitting the small residual `δ(θ)` to `δ(θ_GT)` — a small-signal problem
with weak gradients for parameters that affect `align` and `raytrace` oppositely. In
`L2_correct` the motors are fixed, so the *entire* effect of `θ` shows up in the spot →
fuller-signal, better-conditioned gradients and improved identifiability. So the correct form
likely helps convergence, not just correctness.

### 4.6 Code change

The mechanism already exists — `kinematic._compute_orientations_from_motor_positions(m_c, …)`
(the same call `NormalAlignmentLoss` uses). Stage 2 sets orientations directly from
`train_motor_pos` instead of calling `align_surfaces_with_incident_ray_directions(aim=centre)`,
then traces and applies `FocalSpotLoss` against `train_centroids`.

> **Wiring caveat to verify first:** confirm the ray tracer reads orientation from the state
> that `_compute_orientations_from_motor_positions` writes, vs. the state `align_surfaces`
> sets. That is the one detail to check before trusting the swap.

## 5. The mathematics in one place

Notation (fixed sun `s` per sample; suppress `s` where unambiguous):

* `θ`     — kinematic parameters being optimised; `θ_GT` — ground truth.
* `A_θ(a) = align(θ, s, a)` — inverse kinematics: aim point → motors.
* `R_θ(m) = raytrace(θ, s, m)` — forward optics: motors → centroid.
* `δ(θ) = R_θ(A_θ(centre)) − centre` — the surface/canting offset (why `A` and `R` aren't inverses).

**Generation (synthetic):**
```
m_c  = A_{θ_GT}(centre)
c_gt = R_{θ_GT}(m_c) = centre + δ(θ_GT)
```

**The one physical truth (holds for real data too):**
```
R_{θ_GT}(m_c) = c_gt
```

**The four formulations:**

```
Stage 1 current :  L = ‖ A_θ(centre) − m_c ‖      min at θ_GT only because m_c := A_{θ_GT}(centre)  [circular]
Stage 1 correct :  L = ‖ A_θ(c_gt)   − m_c ‖      proxy; residual ~ δ at θ_GT; real-data valid
Stage 2 current :  L = ‖ R_θ(A_θ(centre)) − c_gt ‖   θ enters twice; breaks on real data
Stage 2 correct :  L = ‖ R_θ(m_c)        − c_gt ‖   exact at θ_GT; real-data valid; cleaner gradients
```

**Recovery guarantees at `θ = θ_GT`:**

| Formulation | synthetic | real |
|-------------|-----------|------|
| S1 current  | exact 0 (circular) | biased |
| S1 correct  | ≈0 (residual `δ`)  | ≈0 (residual `δ`) |
| S2 current  | exact 0            | biased |
| S2 correct  | exact 0            | exact 0 |

The corrected pair is the only one that is valid on real data, internally consistent (both
encode `m_c ↔ c_gt`), and — for Stage 2 — exact. Stage 1 stays a deliberate cheap proxy whose
residual Stage 2 cleans up.

## 6. Summary of required changes — IMPLEMENTED

Status: applied in `single_heliostat/train.py` and `single_heliostat/config.py`. Each fix is
behind a config flag so the legacy behaviour can be reproduced for ablations.

| Component | Change | Flag |
|-----------|--------|------|
| `generate_dataset.py` / `_forward_pass` (generation) | **none** — keep aiming at centre | — |
| `calibration_properties.json` / `SyntheticDatasetParser` | **none** — `c_gt`, `m_c`, `s` already saved/loaded | — |
| `train.py` Stage 1 (train + val sub-loops) | aim the inverse map at `train_centroids` (`c_gt`) instead of `get_centers_of_target_areas` | `STAGE1_AIM = "centroid"` (vs `"center"`) |
| `train.py` Stage 2 (train + val sub-loops) | orient from `train_motor_pos` (`m_c`) via `align_surfaces_with_motor_positions`; drop the `align(aim=centre)` call | `STAGE2_ALIGN = "motor_positions"` (vs `"incident_rays"`) |
| `train.py` Evaluation + diagnostics (`_eval_test`, `capture_trails`) | orient from the recorded GT motors `m_c`; error = `‖raytrace(θ, sun, m_c) − c_gt‖`; the original aim point is never used | `EVAL_ALIGN = "motor_positions"` (vs `"center"`) |
| `utils/synth_data.py::_forward_pass` | new optional `motor_positions` arg: orient from motors when given, else aim-at-centre (generation still needs centre) | — |

Both fixes are the same idea applied to the inverse (Stage 1) and forward (Stage 2) halves of
the calibration: **use the real observables `m_c` and `c_gt`; never the intended aim point.**

### Implementation notes / things verified

* **ARTIST already exposes the forward map.** `align_surfaces_with_motor_positions` →
  `motor_positions_to_orientations` → `_compute_orientations_from_motor_positions` routes the
  recorded motors through the optimizable deviation/actuator parameters (so `θ` gradients flow)
  and applies the **same** `_apply_initial_orientation_offsets` as the incident-ray path —
  frame-consistent. The motors themselves are detached dataset constants, so no gradient flows
  through `m_c` (motors fixed, `θ` varies — exactly the calibration we want).
* **Base-position deviation still flows** in both stages: it is injected into
  `active_heliostat_positions`, which `_compute_orientations_from_motor_positions` reads.
* **Real-data path works unchanged.** `PaintCalibrationDataParser` returns the same 6-tuple
  with **real recorded motors** `[N, 2]` and UTIS-extracted focal spots, so `DATA_MODE="real"`
  feeds `m_c` and `c_gt` straight into the corrected stages. On real data this is the *only*
  valid formulation.
* **Evaluation is centre-free too.** Like training, the test metric never touches the original
  aim point. It feeds the held-out recorded motors `m_c` through the model optics and measures
  the landed spot vs the observed centroid `c_gt`: `err = ‖raytrace(θ, sun, m_c) − c_gt‖`,
  reported in mrad (`/ hel_dist`). This uses only real observables, is exact at `θ_GT`, and is
  the forward dual of Stage 1's inverse check. `capture_trails` uses the same convention so the
  convergence curves match the final eval. The legacy centre-aim eval is still available via
  `EVAL_ALIGN = "center"` for ablation. (An equally valid alternative metric is the *inverse*
  one — aim the model at `c_gt`, compare predicted motors to `m_c` — which is literally Stage 1's
  loss on the test set; the forward metric is chosen here because it stays in interpretable
  focal-spot mrad and is exact at the ground truth.)
* **Caveat — centroid augmentations.** `SyntheticDatasetParser` can shift `c_gt` to emulate
  backlash / gravity sag (`_backlash_amplitude_rad`, `_gravity_sag_amplitude_rad`; both default
  0). When non-zero, they shift the centroid but **not** the motors, so `raytrace(θ_GT, m_c) ≠
  c_gt` by that amount — an intentional, irreducible error floor the kinematic model can't
  absorb. Harmless at the default (0), but keep in mind if you enable them.
